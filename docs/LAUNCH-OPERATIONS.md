# NexAdvisor launch operations

Implemented 17 October 2026. This is a simulator-supported pilot, not a connected real-money marketplace.

## Product operations

- `/support`: participant-owned cases for no-show, late cancellation, failed meeting, dispute and other issues. Each participant has one case per booking. Repeated submissions reuse its reference. Admins can reopen a resolved case for follow-up.
- `/admin/operations`: private case responses, full simulated refunds, no-show recording, deletion requests, internal reconciliation and launch evidence. Every administrative mutation records an audit event. No-show alone cancels the booking but holds the money; reopen and resolve the financial outcome separately. There is no automatic forfeiture rule.
- `/earnings` and `/admin/settlements`: snapshot gross, commission, expert share and payout state. New charges use 25% commission rounded half-up to a minor currency unit. Historical payments retain zero commission. Payout requires paid + completed, 48 hours after session end, and no open case. Duplicate actions do not create another payment/refund/payout. Refund after a simulated payout records simulated recovery of the expert share; this is not a bank transfer or an enforceable recovery guarantee.
- Client self-cancellation is permitted with a full refund at least 60 minutes before start. Inside that window, support reviews the request and the session remains confirmed until resolved. Expert self-cancellation before start refunds in full. After-start problems go through support.
- `/privacy-requests`: account holder requests deletion, admin reviews identity and obligations, then anonymizes. Active bookings, unresolved participant cases and held funds block anonymization. Login is disabled, sessions/tokens revoked, profile/photo and authored content scrubbed. Restricted financial IDs, audit trails and policy consent remain. Operators must separately handle mail previews, copies, provider data and backups under the final retention policy. Do not promise total erasure from all systems. There is no automatic retention duration because the business has not supplied one.
- `/policies`: owner-supplied business name/country/email, commission and refund rules; factual pilot privacy notice. New signup records policy version 2026-10-17. Existing accounts are not retroactively claimed to have accepted it. Registered entity/address, retention periods, tax treatment and final policy review remain launch inputs.
- V10 retires the three known fictional seed experts without deleting booking history. New demo seeding is disabled unless `nexadvisor.demo.seed-enabled=true` is deliberately set. Do not enable it on a public deployment. Real identity and credentials must be reviewed by a human; no real experts have been approved by this change.

## Cashfree integration boundary

No live Cashfree credentials, outbound order/refund/payout requests, bank details or checkout are used. `PAYMENT_SIMULATION_ENABLED=true` remains required for the pilot. Cashfree receipt verification is based on the official [PG signature documentation](https://www.cashfree.com/docs/payments/online/webhooks/signature-verification): HMAC SHA-256 over timestamp followed by exact raw bytes, Base64 signature and constant-time comparison.

`POST /api/v1/webhooks/cashfree` is disabled with 503 unless `CASHFREE_WEBHOOK_SECRET` is configured. It limits body size, checks the signature, and stores only a SHA-256 digest with `VERIFIED_NOT_APPLIED`. Repeated identical payloads are deduplicated. No body containing customer information is stored. Receipt replay is harmless: no booking or ledger mutation occurs. This endpoint is a receipt-only integration seam, not a finished Cashfree payment processor. Use only a sandbox secret while piloting.

Before enabling money: implement server-created Cashfree orders, bind order IDs/attempt IDs to server booking amounts and currencies, verify provider state, process success only once, handle out-of-order callbacks, expired reservations and late success via refund/reconciliation, add verified beneficiary onboarding and provider payout/refund state machines. Choose the appropriate Cashfree marketplace arrangement for the business, validate sandbox scenarios and publish live payment/tax terms. Do not just switch the simulator off and assume a real provider activates. The current database explicitly prevents a live payment provider from being recorded.

## Host operations tooling

`deploy/operations/` contains Nginx rate-limit/TLS templates, systemd service/timer files, and an environment example. `scripts/operations/backup.mjs` creates a PostgreSQL custom-format dump from the existing Compose database, uploads to an encrypted restic repository, checks repository metadata, records successful completion and removes its own local dump only after success. A failed dump/upload/check never advances the success marker. Failed dump files remain private for diagnosis. Schedule retention/pruning only after deciding the business retention policy; the script does not delete remote snapshots.

`monitor.mjs` checks public HTTPS and the database-backed categories API, available disk space and backup freshness (26 hours). It sends a JSON `{text: ...}` alert to a configured HTTPS destination on a change, recovery, or hourly ongoing failure. It does not print webhook credentials. A host outage requires an external uptime monitor because a stopped host cannot run this job. Review support/deletion queues and failed emails from the admin desk; these are not included in anonymous public monitoring.

### Install on a Linux host (not yet performed)

1. Choose hosting, storage region and an off-host backup destination. Install Docker Compose, Node 22, restic and Nginx. Obtain TLS certificates for the actual domain. Keep API/database private.
2. Use `/opt/NexAdvisor` or update unit WorkingDirectory. Create a dedicated `nexadvisor-ops` system account with access to Docker (Docker access is effectively host administration). Create `/var/lib/nexadvisor-ops` owned by that account with mode 0700.
3. Copy `ops.env.example` to `/etc/nexadvisor/ops.env`; fill the real HTTPS origin, private alert destination, off-host RESTIC_REPOSITORY and storage credentials. Put the repository password in a private file and set RESTIC_PASSWORD_FILE. Initialize the repository with `restic init` under the same environment, keeping recovery credentials off-host. Protect environment/password files with 0600 permissions.
4. Install the Nginx template in the appropriate http context and verify `nginx -t` before reload. If using a CDN/load balancer, explicitly configure its trusted proxy ranges; do not trust arbitrary forwarding headers. The Compose API uses native forwarded-header handling behind the private proxy chain; do not expose its port publicly. Keep all routes through the proxy so its per-client limits apply.
5. Install both `.service` and `.timer` pairs, reload systemd, run backup once and confirm the remote snapshot. Test alert delivery and recovery. Then enable the backup and monitor timers with `systemctl enable --now nexadvisor-backup.timer nexadvisor-monitor.timer`.
6. Configure log rotation, an external uptime monitor and infrastructure CPU/memory alerts. Review the journal for failed jobs. The included monitor does not provide infrastructure-wide observability.

### Restore drill

Select a known successful snapshot using `restic snapshots --tag nexadvisor`; inspect its dump path with `restic ls SNAPSHOT_ID`. Restore that dump to a new private directory using `restic restore SNAPSHOT_ID --target RESTORE_DIRECTORY`. Use `scripts/database-backup.ps1 -Action Restore` with a **new** disposable database, or `createdb` followed by `pg_restore --exit-on-error --single-transaction --no-owner --no-privileges`. Never restore over the running database. Start a separate API against the restored database, compare counts and finance records, authenticate a synthetic test account, inspect a booking, and record snapshot ID/date/environment/result in the admin launch checklist. Stop the temporary API afterwards. This must be performed on the chosen hosted backup setup; local checks do not prove hosted recovery.

## Physical acceptance

An operator records actual evidence for expert identity, iOS/Android/desktop Zoom or Meet admission, HTTPS, off-host backup, restore and policy review. Evidence is dated and attributed to the administrator. The UI does not invent a passing status. Test a real appointment end to end, including waiting room/passcode behavior, cancellation, late-cancellation support, missing meeting links and account deletion. No real meeting, physical device or hosted environment has been tested by this implementation.

Deployment target confirmed: Debian. See [Debian setup](../deploy/debian/README.md) and the opt-in operations installer.


## Scheduling and account controls (V11)
- Both participants can propose a new time from Bookings. The other participant must accept, while the existing appointment is at least one hour away. New times must be at least one hour away and within 90 days. Requests do not reserve a second slot. Acceptance locks both accounts and rechecks both calendars, time off and open support cases. Original price, currency, duration and payment remain unchanged. Decline/withdraw leaves the appointment unchanged. One pending request per booking; duplicate requests and decisions are safe to retry.
- Acceptance invalidates old queued notices and the old meeting link. Participants must update their calendar copies; experts must create/update the external meeting and add its link again. No Zoom or Google Meet API is connected.
- Experts select a named timezone for recurring hours. Existing schedules migrate as UTC; editing the timezone reinterprets future availability only, never existing bookings. Nonexistent local times and sessions spanning a DST clock change are skipped. Repeated local starts appear as distinct UTC offsets. Time off remains stored as absolute instants.
- Dashboard and Bookings show confirmed meetings in the next 24 hours without links, plus pending time-change requests. Missing-link reminders go only to the expert, once per appointment start. Delivery rechecks that a link is still missing. All email remains private preview/simulated.
- `/admin/accounts` searches accounts, restricts/reinstates access with a reason and displays the operator audit trail. Restrictions revoke sessions and unpublish the expert. Reinstatement still requires expert approval. Existing bookings remain for support to resolve; the other participant may cancel under the existing refund rule. Administrators cannot restrict administrators here.
- Support outcomes distinguish client no-show, expert no-show and both attended. These require an ended confirmed appointment. No-show cancels and holds funds for a separate financial resolution; attended marks completed. Evidence is recorded in the response and audit. These are operator findings, not automatic video attendance tracking.
- `/privacy-requests` provides immediate irreversible closure after email verification, current-password reauthentication and typed confirmation. Active appointments, unresolved cases and held payments block it. Assisted review remains available. Profile data is anonymized and sessions revoked; financial/audit retention and external copies/backups remain as described above.
