# Debian deployment

For the complete operator procedure, see [Developer SOP](../../docs/DEVELOPER-SOP.md). From the repository root, `sh start.sh deploy https://YOUR-DOMAIN admin@YOUR-DOMAIN` prepares a first deployment; subsequent starts/updates use `sh start.sh deploy`. These commands reuse the deployment tooling described below.

Prepared for a Debian host; not executed on your server. Follow Docker's [official Debian installation guide](https://docs.docker.com/engine/install/debian/) for Docker Engine and the Compose plugin. Install Nginx, restic, Git and a certificate client through your normal Debian package-management process. The host operations jobs require Node 22+; the application runtimes themselves run inside containers. Verify `node --version`, `docker compose version`, `restic version` and `nginx -v`.

1. Put this project at `/opt/NexAdvisor`. Configure `deploy/.env` from its example with your real HTTPS origin, strong database password and initial admin bootstrap. Keep payments and email in simulation. The backend's native forwarding-header handling assumes the supplied private Nginx → Next.js → API chain. Do not publish the API/database ports.
2. For a new deployment, generate private settings with `npm run deploy -- init https://YOUR-DOMAIN admin@YOUR-DOMAIN` (never overwrites an existing file). Run `npm run deploy -- up` to validate, build and wait for healthy services. Use `npm run deploy -- status`, `npm run deploy -- logs`, and `npm run deploy -- stop` for routine console operation. These commands need Node but no host npm dependencies. If you created the environment file manually in step 1, skip init.
3. Point your domain at the host and obtain its certificate. Adapt `deploy/operations/nginx.conf.example` for the actual domain/certificate paths, install it in Nginx's http context and run `sudo nginx -t` before reload. Allow inbound HTTPS/HTTP and your restricted SSH access. Container web binds only loopback; database/API have no host port mapping. If another proxy/CDN is used, explicitly configure its trusted IP ranges.
4. Run `sudo sh deploy/debian/prepare-operations.sh`. It validates Debian/tools, creates the operations account and private state directory, gives that account Docker access, sets group-read access to the deployment environment and installs systemd units. It does not enable schedules, create provider resources, or send alerts.
5. Privately edit `/etc/nexadvisor/ops.env`. Supply the off-host restic repository, its storage credentials and HTTPS alert destination. Create the repository password file owned by `nexadvisor-ops`, mode 0600. The root-owned ops.env is read by systemd and passed to the worker. Initialize the repository once using `restic init` with the same environment; never expose secrets in command arguments or chat. Store recovery credentials somewhere other than this server.
6. Test `sudo systemctl start nexadvisor-backup.service`; inspect `sudo journalctl -u nexadvisor-backup.service` and verify the snapshot remotely. Run a restore drill as described in [LAUNCH-OPERATIONS.md](../../docs/LAUNCH-OPERATIONS.md), then test monitor failure/recovery delivery. Enable schedules only after those pass: `sudo systemctl enable --now nexadvisor-backup.timer nexadvisor-monitor.timer`. Review `systemctl list-timers`.
7. Add an external uptime check for host failure, configure infrastructure resource alerts/log rotation and choose a documented backup retention policy. The supplied jobs deliberately do not prune remote backups without that policy.
8. Remove bootstrap admin environment values after first login. Review policy/business details and onboard real experts. Use `/admin/operations` to record real device calls, support handling, TLS and restore evidence. Existing fictional seed profiles are retired by migration V10.

A Debian OS choice alone does not provide server access, a backup destination or an alert receiver. Those still need configuration on the actual host. Avoid using production data in automated tests. For updates, take an off-host backup first, rebuild, inspect health and migrations, and run a real booking smoke test; never run `docker compose down -v` on the deployment.
